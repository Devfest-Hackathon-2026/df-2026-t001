## 2. 参照リポジトリから取り入れる考え方

`df-hack26` は看護師勤務表向け。介護の欠員補充に合わせて作り直す。出典は提出資料に明記する。

| 考え方 | 内容 | 本製品での使い方 |
|---|---|---|
| 意味境界 | ルールを少数の型に限る。Gemini は型を満たす候補しか出せない | 月次ルールは **5型**（必要人数・希望・連なり・回数・集計）。日次は別のデータ型（§4） |
| 全制約を軟化して最小化 | 絶対/強く/できれば の3段階。基準由来を重く置き、施設の運用ルールが先に破れる | 同じ。仮値の基準は `locked` 扱いで重い罰点 |
| 二度解き | 解けない場合、全硬制約を軟にして「何件破れば通るか」を測る | リーダーに「どのルールが何件破れるか」を提示し、Gemini が1文で説明 |
| 追記専用の編集ログ | 表を上書きせず、提案と手修正の差分を追記 | `facilities/{fid}/edits`（Firestore）→ Pub/Sub → BigQuery |
| 反復検出 | 同じ修正の反復から、ルール候補を見つける。閾値は観測量から計算 | 施設ルールの自動学習。リーダーが範囲と期限を選ぶ |
| LLM の位置 | 初回求解の前には置かない。翻訳と説明だけ | 同じ。Gemini は求解に関与しない |

違い: 介護には看護の「72時間ルール」を持ち込まない。夜勤の偏りや連続勤務などは、施設ごとの仮値として設定する。

## 3. 月次モデル（CP-SAT）

- 変数: `x[従業員, 日, 勤務区分]`（各日・各人でちょうど1つ）。
- 必須（絶対）: 勤務区分ごとの必要人数、資格者の最低人数、連続勤務上限、夜勤明けの翌日の扱い、確定済みセルの固定。
- 軟制約: 希望休・希望勤務、夜勤回数の公平性、連勤の抑制、個人ごとの希望傾向。
- **日次を同時に考える仕組み（集約制約）**:
  - 施設の日課テンプレートから、日ごとの時間帯ブロック（朝・昼・夕・夜間など）の必要人数曲線を作る。
  - 月次モデルに「各日・各ブロックで勤務中の人数 ≧ 必要人数」と「休憩を回せる余裕」を入れる。
  - これにより、日次で解ける月次案を作る。

## 4. 日次モデル（CP-SAT）

月次で確定した各日の勤務者について、1日を解く。

- 業務（食事・入浴・排泄介助・巡回・記録・休憩）を区間変数で表し、担当者に割り当てる。
- 制約:
  - 同じ人の業務は重ならない（NoOverlap）。
  - 休憩は規定の時間窓に収める。
  - 資格が必要な業務は資格者に割り当てる。
  - 勤務区分の時間外には割り当てない。
- 軟制約: 利用者と担当者の継続性（担当の入れ替わりを減らす）、移動の連続性、業務の偏りの抑制。
- 解けない日は、二度解きで「足りない業務枠」を求める。その日・そのブロックの必要人数を上げて月次へ戻し、再求解する（最大2回、時間予算あり）。

## 5. 欠員補充での使い方

- 欠員が出た日のセルを固定し、**最小変更**を目的に月次を再求解する。
- 打診の順位は、Vertex AI の応諾確率（バッチ予測）と、CP-SAT で成立する候補を組み合わせる。
- 補充後は、その日の日次スケジュールだけを再求解する。
- 補充の採用・却下は、編集ログに追記する。

## 6. 学習ループ（施設ごと）

1. リーダーの手修正を、編集ログに追記する（月次は「人・曜日・外された勤務」、日次は「人・時間帯・業務」を鍵にする）。
2. 鍵の数と月あたりの手修正から、反復の閾値を毎月計算する（固定値は使わない）。
3. 反復を検出したら、1画面1問でルール候補を出す。範囲（この人だけ / この曜日 / 全員）と期限はリーダーが選ぶ。
4. 承認されたルールは、来歴と期限付きで施設のルール一覧に入る。使われない・期限切れのルールは止まる。
5. BigQuery の特徴量（修正率・応諾履歴）が週次の学習に入り、施設別の応諾予測と需要予測を更新する。

## 8. 合成日課（施設ごとの癖）

3施設で日課テンプレートを変える。例:

- 特養: 入浴は午前・午後の2波、食事介助の必要人数が多い。
- 有料老人ホーム: 個別対応が多く、夕方に業務が集中。
- グループホーム: 少人数で、調理・見守りが中心。

日課は「時間帯 × 業務 × 必要人数 × 必要資格」で表す。再現できるよう乱数シードを固定する。

計測条件: 手元のMac（12コア、CP-SAT のワーカー8本）。「破れ」は同じルール一式（仮値）と希望休を、ソルバーとは別の純Pythonの検証器（`verify.py`）で数えた件数。

実装したこと:
- **DSL**: 月次5型（必要人数・希望・連なり・回数・偏り）と日次1型（人×業務×時間帯の回避・希望）。不正なルール（上下限なし、型の混在、3段階以外の強度）は読み込みで弾く。
- **月次**: 絶対は硬制約、強く/できれば は罰点。日課テンプレートから導いた「時間帯ごとの必要人数・資格者数」を集約制約として入れ、日次で解ける月次案にする。資格者は同時に走る業務の分を足し合わせる（最初は max にしていて、ひだまりの家で認知症ケア要員が足りず17件未割当になった。足し合わせに直して解消）。
- **二度解き**: 解けないとき、絶対を全部軟にして最小の破りを測り、「どのルールを何件」を文章にする（時間上限8秒。最小と証明できない場合はそう表示）。
- **日次**: 業務を30分刻みの枠×人数に分け、在席・資格・退勤上限・休憩（6時間以上の在席者）を満たして割り当てる。担当の継続性と業務量の偏りは軟制約。足りない業務は未割当として原因付きで返す。
- **月次↔日次の連携**: 日次で足りなかった時間帯・資格を月次へ戻して再求解（最大回数あり）。合成の小さな施設で、1回目は未割当28件、2回目で0件に収束することをテストで確認した。実データの3施設では1回目で未割当0だったため、実運用の施設でループがどれだけ効くかは、検証していない。
- **欠員補充**: 欠員セルを固定し、元の表からの変更を最小にして再求解（`baseline`、`fixed`）。テストでは変更12セル以内。
- **独立検証**: ソルバーの出力はすべて検証器で破れ0。検証器はリーダーの手修正やAI案のチェックにも使える設計。

P1 のデータの変更（再投入済み）: 日課テンプレートを、基準人数で在席が足りる時間帯に収まるよう調整（さくら苑の朝7時台、みどりの丘の朝と夕方）。11・12月の希望休も `fact_requests` に追加（計2,865行）。

P2 の時点で残っていた課題と、その後の結果:
- Gemini によるルールの翻訳と説明の言い換え（P4 で実装。§9.8）、反復検出（P5 で実装。§9.9）、API 化（P3 で実装。§9.7）。P2 の時点では、説明文は決定的なテンプレートだった。
- **Cloud Run の資源**: 当時の Terraform（`care-api` 用）は CPU 1・メモリ512MiB・最大3インスタンス。上の計測は12コアの手元なので、1 vCPU で同じ速度は出ない。P3 で新しいサービス `care-solver-api` を 4 vCPU・2GiB にし、実環境で計測した（§9.7）。
- 日次は日課テンプレート単位の継続性のみ。利用者（入居者）単位の担当の継続性は、データが無いため扱っていない。みどりの丘・ひだまりの家の担当入れ替わり（75・48回/月）は重みの調整余地がある。
- 退勤上限（leave_by）がある人は、月次の集約制約でその時間帯に数えない保守的な扱い。人員を余分に置く可能性がある。
- 月次の目的関数は、ルールの破れの最小化が中心。公平性や希望の細かい重み付けは、リーダーの反応を見て調整する想定。

| `GET/POST /rules` `POST /rules/{id}/stop` | ルールの参照・追加（DSL で検証）・停止（履歴を残す） |

表を上書きする API は無い（PUT/PATCH/DELETE は 405）。業務イベントは Pub/Sub → BigQuery `events_raw` に流れることを実環境で確認した。

実環境の求解時間（4 vCPU、月次11月。手元の Mac は 0.2〜0.6 秒＋日次 0.4〜7 秒）:

| 施設 | 月次＋日次30日（合計） | 未割当 |
|---|---|---|
| さくら苑（34名） | 7〜12秒（月次 1.7〜1.8秒） | 0 |
| みどりの丘（22名） | 19秒（月次 1.6〜2.2秒） | 0 |
| ひだまりの家（16名） | 2.2〜2.6秒 | 0 |

最初の実測（v1）では日次が重く、みどりの丘で 28〜32 秒、さくら苑で 15〜20 秒だった。日次は「全業務を割り当てられるか」が分かれば連携には十分なので、1日あたり 1 秒・全体 40 秒の時間予算を設けて v2 にした（未割当は 0 のまま）。単一スレッド化や日ごとの並列化は試したが、最適性の証明が長引いてかえって遅くなったため採用していない。

乱用対策（実環境で確認）: IP ごとに重い呼び出し 6回/分・軽い呼び出し 120回/分（8回目までに 429）、同時求解 2 本（空きがなければ 503）、本文 64KB 超は 413。

デプロイで分かったこと:
- 新しいサービスアカウントへのロール付与後、**約10〜15分間、Firestore が間欠的に 403（API では 500）を返した**。時間が経つと収まった。再デプロイ後も、新しい SA を足したら同じ待ち時間を見込む。
- 複合インデックスが要るクエリ（`month` で絞って `created_at` で並べ替え）は、`month` だけで絞って Python 側で並べ替えるよう直した（件数は月に数件）。
- Firebase Hosting の `firebase.json` では、`/api/**` は画面状態の同期用の `care-api` に向いている。最適化ソルバー `care-solver-api` は、画面が CORS で直接呼ぶ（CSP の `connect-src` で許可）。Hosting は P6 でデプロイした（https://care.yutok.dev/）。

運用スクリプト（`solver-api/scripts/`）: `smoke.py`（通し確認。実環境で全件 OK）、`reset_demo.py`（デモ状態に戻す）、`seed_rules.py`（初期ルールを DSL の形で投入）。

P3 の時点の注意と、その後:
- **書き込み系の API も公開で、認証が無い**。誰でも手修正・欠員・ルールを追記できる（審査用の公開デモとして承知の上）。壊されたら `reset_demo.py` で戻す。ルール追加は入力検証と 64KB 上限のみ。
- レート制限はインスタンスごとのメモリ上（最大3インスタンスで最大3倍まで通る）。IP は `X-Forwarded-For` の末尾を使う。画面は Hosting を通さずに Cloud Run を直接呼ぶため、末尾は Cloud Run が付ける利用者の IP になる。
- 実環境のテスト実行が `care_analytics.events_raw` に本物のイベントとして残っている（`roster_proposed` 12件ほか）。P5 の学習では、合成データ（`synthetic=true`）と同様に除外する条件が要る。
- P3 の時点の候補の順位は「同じユニット・今月の勤務の少なさ・新たに破るルールの少なさ」で、受諾確率（`accept_probability`）は null だった。P5 で学習した応諾予測を入れた（§9.9）。
- 既存 `care-api` の Terraform 差分（スケーリング表記）は適用していない（実質差なし）。

## 9.8 P4 の結果（Gemini：ルール翻訳・説明の言い換え・チャット）

`care-solver-api` に 3 つのエンドポイントを追加（イメージ v4 をデプロイ済み）。Gemini は Vertex AI の `global` エンドポイントを ADC（サービスアカウント）で呼ぶ。API キーは存在しない。コードは `solver-api/care/ai/`、評価は `solver-api/scripts/eval_ai.py`。

| エンドポイント | モデル | 役割 |
|---|---|---|
| `POST /facilities/{fid}/rules/translate` | `gemini-3.1-pro-preview` | リーダーの言葉 → ルール候補（範囲ごと）。**保存はしない** |
| `POST /facilities/{fid}/explain` | `gemini-3-flash-preview` | 違反・日次の説明の言い換え（事実の検査つき） |
| `POST /facilities/{fid}/chat` | `gemini-3-flash-preview` | 関数呼び出しで施設のデータを調べて答える |

**方針（参考: df-hack26 の設計の考え方。コードは複製していない）**
- **翻訳**: LLM は DSL の型を満たす「下書き1本」しか出せない（`response_schema`）。ラベル（リーダーが読む1行）は LLM に書かせず、下書きの項目から決定的に作る。範囲（この日だけ／この人の曜日／この人の毎日／全員）はリーダーが候補から選ぶ。言葉に曜日が明示されたときはそれを優先する。候補ごとに「今の表で破れる件数」を決定的に見積もる。下書きは検証し、通らなければ 422（推測で補わない）。
- **説明**: 事実の検査（fact-lock）を機械的に行う。元に無い数字があれば不採用、省略された「ルール名」は元の事実の行をそのまま補い（`route="gemini+facts"`）、補えなければ元の決定的な説明を返す（`route="template"`）。
- **チャット**: ツールは読み取り 9 種と「提案」2 種（`propose_edit`, `propose_offer`）だけ。提案は実行せず、実行するときに呼ぶ API と、実行した場合のルール違反の見積りを返す。表・欠員・ルールを書き換えるツールは存在しない。ツールが返す文字列（ルールのラベルなど）は命令として扱わない（システム指示で明示、ラベルは 120 文字で切る）。
- **個人情報**: 入力は、施設の従業員の氏名を ID に置き換え（仮名化）、残りを Sensitive Data Protection で伏せ字にしてから AI に渡す（氏名・電話・メール・住所・マイナンバー）。マスクできなければ AI を呼ばない（fail closed）。実環境で「氏名・電話・メールを含む入力」が `HDM-007さんは…連絡は [PHONE_NUMBER] か [EMAIL_ADDRESS] まで` になることを確認した。
- **費用の上限**: 全体 1 日 600 回、IP ごと 1 日 40 回（Gemini の呼び出し回数。当初はリクエスト単位で 300 回・20 回だった。Firestore `aiUsage` のカウンタ、JST の日付）、IP ごと 10 回/分。入力 2,000 文字、履歴 10 件まで。実環境でカウンタの加算を確認（超過時の 429 はテストで確認し、実環境では確認していない）。
- **記録**: 各呼び出しを `ai_call` イベント（機能・モデル・トークン数・所要時間）として Pub/Sub → BigQuery に流す。

**評価（本物の Gemini、決定的な指標。`eval_ai.py`）**

| 項目 | 結果 |
|---|---|
| 翻訳（Pro） | 全項目一致 **22/22**、無関係な発話を弾く 3/3、API エラー 0、中央値 3.8 秒（最大 5.6 秒） |
| 翻訳（Flash） | 全項目一致 21/22、弾く 3/3、中央値 3.0 秒（最大 12.4 秒）。Pro が 1 件分正確だった |
| 説明の言い換え | 16 件中 15 件を採用（そのまま 8、省略されたルール名を補って 7）、1 件は元の説明に切り替え |
| チャット | 期待するツールを呼んだ **11/11**、返答に元に無い数字 0、提案が実行された 0。中央値 2.9 秒（最大 9.5 秒） |
| 個人情報マスク | 氏名・電話・メール・住所を伏せ字、従業員 ID（`HDM-007`）は残る |

評価の限界: 発話・質問は 22 件・11 件と少なく、開発者（AI のコーディング支援を使って）が書いた。温度 0 で 1 回ずつの測定で、独立した検証ではない。Vertex AI の Gen AI 評価サービスは使っていない（決定的な指標で足りると判断）。

**評価で見つけて直したこと**
- 説明が内部キー（`dementia`・`rec`・`watch`）のまま出ていた → 日本語の語彙（`vocab.py`）を通す。
- チャットが年を推測して「2024年」と答えた → 「今見ている月」をモデルに渡す。ツールが失敗したら推測しない、と指示。
- 「休みにしたら問題は出ますか」で調べる回数の上限に達して答えが出なかった → 上限に達したら、ツール無しでここまでの結果だけで答えさせる。
- 言葉の「木曜」がセルの曜日（月曜）に上書きされた → 言葉で明示された曜日を優先。
- 「無理」に強度の指定（絶対）を付けた誤り → 強度は明示された言葉のときだけ。
- 評価スクリプトがエラーの呼び出しを集計から落としていた → エラーを失敗として数える。

**モデルの選択（実測）**: Flash 系のうち `gemini-3.8-flash` は、直列でも 10 回中 2 回エラー、最大 25 秒と不安定だった。`gemini-3-flash-preview` は 10/10 成功・最大 4.2 秒だったため、Flash 系の既定にした。翻訳は Pro が Flash より安定して正確。どちらも preview 系で、将来変わる可能性がある（環境変数 `GEMINI_PRO_MODEL` / `GEMINI_FAST_MODEL` で差し替え）。

**注意**
- Vertex AI は 429（利用枠）や 504（時間切れ）を返すことがある（評価中に Flash で発生）。429/503 は短く待って再試行、504 は再試行せず AI 失敗として返す。チャットは全体 28 秒の予算で打ち切る（Cloud Run の 60 秒に収める）。
- AI の呼び出しは、1 回あたり約 1,000〜1,500 トークン（思考トークンを含む）。単価を確認していないため、費用は見積もっていない。ただし上限（全体 1 日 600 回）があるため、最悪でも日あたりの回数は有限。
- 説明の言い換えは、モデルがルール名を省略しがちで、多くの場合「省略した点」の補足が付く。読みやすさの改善余地がある。
- P4 の時点のチャットは、勤務表・違反・日次・ルール・欠員だけを調べられた。BigQuery の集計（先月の偏りなど）は P5 で追加した（§9.9）。
- 公開 API で認証が無い点は P3 と同じ。書き込みを伴うのは、人が `POST /rules`・`/edits`・`/offers` を呼んだときだけ（チャットや翻訳は書き込まない）。

## 9.9 P5 の結果（Vertex AI Pipelines：応諾予測・反復検出・BigQuery 集計）

**学習パイプライン**（`solver-api/pipelines/`、README あり）。Vertex AI Pipelines（KFP v2）で、`pipeline-sa` が実行する。1 回およそ 12 分。公開 API から起動する経路は無い（課金の悪用を防ぐ）。

```
extract ─┬─ train(施設A) ─┐
         ├─ train(施設B) ─┼─ promote（gate を通ったものを champion に・Model Registry・BigQuery）
         └─ train(施設C) ─┘
detect（手修正のくり返し → ルール候補）は並行
```

- **応諾予測**: 打診の時点で分かる 14 の特徴量（依頼までの余裕・勤務区分・連勤・当月の勤務時間・最近の打診回数・その人の過去の応諾率など。結果や応答時間は入れない）。施設ごとに、ロジスティック回帰・XGBoost・プール学習（他施設の打診も使う）を、5 分割×2 回の交差検証で比べて選ぶ。基準（件数に依らない基本確率）に勝てなければ昇格しない。
- **推論**: 登録した champion モデルを API が GCS から読み込み、打診の時点の特徴量で採点する（純 Python。xgboost・sklearn は API に入れない）。Endpoint は作らない（常時課金なし）。パイプラインは out-of-fold の予測を BigQuery `care_ml.offer_scores` に書き、較正の監視に使う。
- **Model Registry**: `care-acceptance-<施設>` を登録（エイリアス `champion`）。ただしデプロイはしない。
- **スケジュール**: 週次（月曜 03:00 JST、Vertex AI の PipelineJobSchedule。有効）。版名は実行ごとのジョブ ID（`run-…`、上書きしない）。実行はこれまでに 4 回（3 回目は、ジョブ ID が数字だけで BigQuery が整数と誤判定して失敗 → 版名に接頭辞・BigQuery のスキーマを明示して修正、4 回目で成功）。

**施設ごとの結果**（交差検証、合成データ。AUC は 0.5 が当てずっぽう、1.0 が完全）

| 施設 | 打診数 | 採用 | AUC | 基準より対数損失がよい | 比べた他の候補（AUC） |
|---|---|---|---|---|---|
| さくら苑 | 412 | ロジスティック | 0.772 | +18.1% | プール 0.775 / XGBoost 0.746 |
| みどりの丘 | 320 | プール学習 | 0.695 | +7.4% | ロジスティック 0.662 / XGBoost 0.615 |
| ひだまりの家 | 164 | **昇格せず** | 0.522 | −10.1%（基準に負ける） | ロジスティック 0.453 / XGBoost 0.460 |

- **XGBoost は 3 施設とも負けた**（件数が少ない）。それでも候補に残し、選ぶ根拠を成果物に記録している。
- **ひだまりの家は基準に勝てず、昇格しなかった**。この施設は従来の順位付けのまま（API の応答にも理由を出す）。データが貯まれば、次回以降の学習で昇格し得る。検査に通すための調整はしていない。
- **候補の順位への反映**（実環境で確認）: 欠員を登録すると、ルール違反を起こさない候補に「応諾の見込み 41%」と、影響の大きい要因（「依頼までの余裕がマイナス」「この人の過去の応諾率がプラス」など）が付き、見込みの高い順に並ぶ。余裕のある欠員は、直前の欠員より応諾確率が高くなることをテストで確認。
- **学習が進む仕組み**: 打診のとき、特徴量を打診の記録と `offer_sent` イベントに残す。イベントは BigQuery に流れ、次回の学習が `fact_offers`（合成）に加えて使う。実運用の打診は、これまでに 1 件（私の動作確認）のみ。**その 1 件は実際に次の学習に取り込まれた**（さくら苑の学習データが 412 → 413 件、`live_rows=1`）。ただし公開デモの API は認証がなく、誰でも打診・応答を書き込めるため、提出直前に既定を変えた：イベントに出どころ（`source`、公開デモは `public_api`）を付け、学習は既定で合成データだけを使う。実運用のイベントはパイプラインの `live_sources` で出どころを明示したときだけ、職員ごと・IP ごとの件数の上限つきで取り込む（`care/learn/steps.py`）。学習履歴は `GET …/models/acceptance` と `care_ml.model_runs` で見られる。

**反復検出**（リーダーの手修正のくり返し → ルール候補）
- 鍵 =（人, 曜日, 外された勤務）。閾値は固定の「3回」にせず、鍵の数と手修正の数から、偶然の重なりが観測期間に 0.25 件を超えない最小の回数を二項分布で計算。日次（人×時間帯×業務）も同じ方法。
- 合成データに埋め込んだ「隠れたルール」との照合: **月次 9 件中 7 件を再現、誤検出 0 件。日次 7 件中 7 件を再現、誤検出 0 件**。未検出の 2 件は、観測期間中に 3 か月も繰り返されなかったもの。
- API: `GET …/learned-rules`（根拠・質問文・「ずっと／3か月だけ」の選択肢・今の表で破れる件数）、`POST …/learned-rules/dismiss`、採用は `POST …/rules`。採用・却下したものは二度と出さない。範囲と期限は人が選ぶ。

**チャット**に、学習モデルの状態・反復検出の候補・BigQuery の集計を調べるツールを追加（集計は決まった 5 種の問い合わせだけで、自由な SQL は受け付けない。BigQuery は読み取り専用・1 回 50MB まで）。本物の Gemini で 17 問中 17 問が期待どおりのツールを呼んだ。集計の答え（勤務区分別の応諾率 58.3 / 54.6 / 49.4 / 30.7% など）は BigQuery の値と一致を確認。

**テスト 67 件**（P5 時点。現在は 203 件。採点が sklearn・XGBoost の予測と一致、gate、検出の再現率と誤検出、API への反映、チャットのツールなど）。

**注意**
- **学習データは合成（架空）が中心**。上の精度は「合成データに埋め込んだ傾向を再現できた」ことを示すもので、実運用での精度ではない。順位付けの効果は、AUC・対数損失でしか測っていない（本物の打診での A/B は無い）。
- 特徴量の `offers_last14`・`month_hours_before` は、API では同じ月のデータから近似している。
- **ベクトル検索（類似ケース）は実装していない**（締切を考慮して見送り）。
- Vertex AI Pipelines の費用は確認していない（1 回 12 分・小さな学習。単価は未確認）。
- 反復検出・学習の成果物は、パイプラインを回した時点のスナップショット。次回の実行まで更新されない。
- 実環境の動作確認で作った打診が、`events_raw` に実運用の打診として 1 件残っている。

重い呼び出し（`solve-inline`・`replan-inline` を含む）は、IP ごとに 6 回/分。AI の呼び出しの上限は、施設の API が全体 1 日 600 回・IP ごと 1 日 40 回（Gemini の呼び出し回数で数える。提出直前に、リクエスト数から変更）、意図の分類が IP ごと 1 日 150 回・全体 1 日 2,000 回（入力 300 文字まで）。

**測定**: 月次 `solve-inline`（実環境の Cloud Run、34 名）は約 2〜4 秒で最適解、`replan-inline` は約 0.2 秒、`candidate-reasons`・`employee-compose` の Gemini は 1〜2 秒（初回は数秒）。

**CI/CD**: `.github/workflows/deploy-solver.yml`（テスト → イメージのビルド → Cloud Run → healthz）と `deploy-gcp.yml`（`care-api` と Hosting）。WIF で鍵なし。この提出用リポジトリでは Actions が使えないため、開発用リポジトリで稼働している。

**テスト**: solver-api 203 件（`cd solver-api && python -m pytest -q`）、care-api 18 件（`cd api && python -m pytest -q`）。

**実装しなかったもの（見送り）**: ダッシュボードの Looker Studio 埋め込み、ベクトル検索（類似ケース）、Vertex AI の Gen AI 評価サービス、予算アラート。

## 10. リスクと、検証していない事項（計画時のリスクと、完了後の状態）

- 計画時のリスク: 残り約1日で範囲が広い。P3 までは機能追加を止める方針だった（P6 まで完了）。
- 日次ソルバーは、利用者単位の担当継続性を入れると変数が増える。60分枠から始め、時間が許せば30分枠にする。
- 反復検出は履歴が貯まるまで効果が見えない。合成データには、反復する癖を意図的に埋め込む。
- `df-hack26` の実測（月次 約0.3秒、日勤段 約0.07秒）は看護12人・30日の規模だった。本製品の規模と日次モデルの速度は、§9.6・§9.7 で実測した。
- 仮の基準値は法令の正確性を保証しない。画面と資料に「デモ用の仮値」と明記する。
- 予算アラートは設定していない（課金アカウントの権限がない）。課金は手動で確認している。

## 11. 提出直前の修正（2026-11-10）

提出前のレビューで見つかった問題を直した。主なもの：

- **画面の状態同期**: `public/sync.js` が古い保存キー（v7）を見ていて、別の端末には同期されていなかった（同じブラウザの 2 タブでは動いて見えた）。キーを揃え、`PUT /api/state` を版数つき（`{base, app}`、不一致は 409）にし、端末側で 3 方向マージ（id ごと）して送り直すようにした。同時に更新しても、どちらの変更も消えない。
- **care-api**: 画面から使っていない `/api/ai/*`・`/api/seed`・`/api/analytics` を削除。状態の形・大きさの検査、IP ごとの書き込み上限、リセットの条件（専用ヘッダー・間隔）、本文の大きさの上限（chunked も）を追加。
- **欠員・打診**: 終わった欠員（充足・組み直し済み）への打診・受諾・組み直しを 409 に。打診先と受諾時に、本人・当日の勤務・必須ルールを検査。受諾は原子的に 1 件だけ通る。ID は衝突しない形に。再度の solve では、欠勤・補充・組み直しを固定セルとして引き継ぐ。
- **ルール**: 期限（`expires_on`）を日ごとに反映。日次ルール（taskRequest）を保存できるように。必須ルールの値の範囲を検査し、固定の初期ルールは止められない。デモのリセットで初期ルールを元に戻す。
- **AI**: チャットの履歴・plan-intent の職員名・説明のルール名も仮名化＋マスク。履歴の assistant 発言は引用データとして扱う。説明・理由の事実検査を強化（URL・連絡先・指示めいた文・事実に無い評価語を不採用）。チャット全体の時間の上限と、ツール（求解系は 2 回まで）の上限。エラーの詳細は返さずログに残す。
- **乱用対策**: 本文の上限を実際に読んだバイト数で判定。`/employee-compose`・`/candidate-reasons` を AI 枠に、`/rank-candidates` を重い呼び出しに分類。AI の上限は Gemini の呼び出し回数で数える。
- **学習**: 公開デモのイベントは既定で学習に使わない（§9.9）。XGBoost が勝ったときも Model Registry に登録できるように（失敗は握りつぶさない）。
- **画面**: 夜勤の翌日（明け）に勤務がある人を打診しない（生成・検査と基準を統一）。日付の読み取り（年・月またぎ、実在しない日付）。締切後はチャットからも希望休を受け付けない。デモの時計が日付をまたぐと「今日」も進む。CSP から `script-src 'unsafe-inline'` を削除。
- **リポジトリ**: `package-lock.json` を追跡し CI は `npm ci`。Python の依存の版を固定。care-api の Gemini モデル名を `gemini-3-flash-preview` に統一。
